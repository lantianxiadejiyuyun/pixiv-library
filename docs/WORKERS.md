# 队列进程与 CPU 分配

服务默认使用一个 Web/API 进程和八个工作进程：手动下载、失败重试、自动下载、详情解析、作者与订阅检查、AI 识别、AI 汉化、其他任务。工作进程只领取自己的队列，数据库仍统一持久化任务、租约、账号分配和并发限制。用户在任务中心、账号管理中设置的上限继续生效。

每个工作进程只有一个领取调度器，按需要创建最多 8 个任务线程；空闲或暂停时不会让任务线程争抢数据库写锁。每个 MySQL 工作进程使用独立连接池，常驻 2 个连接、最多 10 个，API 保留自己的连接池。领取前先检查暂停、容量和任务存在性；订阅检查使用一次批量查询查重。网络采集的请求间隔与平台退避仍共享，不因拆进程而倍增。

## 默认配置

在 deploy/.env 中可设置：

```dotenv
LIBRARY_WORKER_MODE=process
LIBRARY_CPU_AFFINITY=auto
```

auto 根据当前进程允许访问的逻辑 CPU 分配，尊重容器已有 cpuset。CPU 足够时，API 和各队列使用不同的 CPU 集合；API 先预留 1 个，14 个及以上预留 2 个，剩余均分给八个队列，多余部分分给 AI。核心较少的 NAS 会让部分队列共用 CPU，页面明确提示；单核设备无法做到核心隔离。操作系统拒绝 auto 绑定时保留进程隔离并显示未绑定。off 可显式关闭绑定。

这里的编号是操作系统或 Docker 虚拟机中的逻辑 CPU，不保证对应独占的物理核心。CPU 亲和性限制本项目进程可以在哪些 CPU 上运行，其他程序、MySQL、代理内核和操作系统仍可能使用相同 CPU；不会自动调整第三方 Ollama 服务的 CPU 配置。下载速度还受网络、磁盘、平台响应和账号权限影响。

本机容器可用 16 个逻辑 CPU 时，默认分配如下：

| 进程 | 逻辑 CPU |
| --- | --- |
| Web/API | 0、1 |
| 自动下载 | 2 |
| 详情 | 3 |
| 作者与订阅检查 | 4 |
| AI 识别 | 5、10–15 |
| AI 汉化 | 6 |
| 其他任务 | 7 |
| 手动下载 | 8 |
| 失败重试 | 9 |

## 手动分配

CPU 编号必须来自当前容器或原生进程可用的集合。可以在 deploy/.env 中用一行完整 JSON 覆盖，全部九个角色均需给出非空整数数组：

```dotenv
LIBRARY_CPU_AFFINITY={"api":[0,1],"download":[2],"details":[3],"checks":[4],"ai":[5,10,11,12,13,14,15],"translation":[6],"other":[7],"manual_download":[8],"retry":[9]}
```

旧版显式 JSON 缺少 manual_download 或 retry 时，相应进程沿用 download 的 CPU 集合；可添加对应项单独绑定。

修改后从项目根目录运行 `python scripts/compose.py up -d app`。无结构迁移，不改变队列暂停、账号和订阅设置。CPU 编号越界或 JSON 配置错误会拒绝启动，避免将错误计划展示成已绑定。设定重叠集合时允许共用并在页面提示。

Windows 原生 Python 和 Linux/Docker/NAS 使用相同进程入口。Windows 通过进程亲和性掩码绑定，当前实现面向进程所在的处理器组；超过 64 个逻辑 CPU 的多处理器组部署需要另行验证。macOS 等不提供绑定 API 的环境保留独立进程并显示未绑定。当前 Web 仍以单个 Uvicorn worker 启动；不要用多个 Uvicorn worker 代替队列并发设置。

## 状态、退出与恢复

队列归类由数据库生成列 `jobs.queue_lane` 随任务类型和 payload 自动计算，领取与状态查询使用 `(queue_lane, status, created_at, id)` 索引。迁移会为已有任务补齐计算结果；普通更新和批量 JSON 更新都会立即重新归类，无需应用层手动回填。它仅加速查询，账号权限、暂停、租约和每账号／每队列并发校验继续执行。MySQL SQL 导出保留生成列定义，但不将生成值写入 INSERT。

任务中心显示 API 使用的 CPU、各队列 PID、操作系统实际 CPU 掩码和进程状态。计划值不会代替实际绑定状态。GET /api/queue/status 新增 runtime，仍需管理员会话，不暴露凭据、内部状态文件路径或任务租约令牌。

工作进程退出后，监督线程仅重启对应队列，并对其最后上报的租约令牌设置过期；未能上报的极短窗口继续由原 300 秒租约回收。重新领取会签发新令牌，旧尝试不能提交。上游失败仍不自动切换账号。重启退避 1–60 秒，存活但心跳超时的进程显示超时，不盲目启动重复实例。DB 恢复操作不占运行状态查询锁。

正常关闭先通知所有工作进程结束，进行有界等待，然后终止仍阻塞的进程。Linux 为每个队列创建进程组，强制结束时同时清理其推理子进程；父进程消失时工作进程也会退出。内置 Mihomo 仍只由 Web 主进程管理，工作进程使用同一回环代理端口，不会各自再启动一个代理。

AI 实际执行设备、CPU 回退和模型状态通过受控的本地心跳文件从 AI 进程返回 API，并在模型文件或设备设置改变时失效。文件只保存运行状态，任务与结果仍写数据库；备份不依赖心跳目录。

## 已验证

采集总暂停只影响自动下载、详情解析和作者／订阅检查。手动下载（含非 Pixiv 的起始资料阶段）保留独立暂停与并发，任务领取、请求前检查、进度检查和 API 展示均遵守这一边界。

采集统一并发设置也只修改自动下载、详情解析和检查三个队列；手动下载的并发仅在自身队列卡片中设置，新库默认 1，已有设置保留。请求间隔和平台 429 冷却仍按请求限速设置执行。

点击失败／取消任务的「加入重试队列」后，该任务进入独立 retry 队列，默认并发 1，自身暂停与并发不受采集统一开关影响。保留原任务功能、下载来源及上次失败原因；其他平台的后续正文阶段仍在重试队列，重试检查发现的新作品进入普通队列。现有失败任务不会自动重放。

Pixiv 账号需同时获得原功能和「重试」权限。图片、手动下载、作品详情、作者资料分别取对应账号池与 retry_account_ids 的交集；关注、收藏或私密目录仍使用原主账号，不能由重试副账号代替。未配置权限时任务明确失败；账号暂时满并发时等待，普通任务与重试共用每账号并发上限。领取、执行、进度检查和提交前校验权限。旧配置不自动授予重试权限，旧客户端保存其他设置时保留已配置的重试权限。

- Linux 隔离容器完整 958 项后端测试通过，包含七个独立工作进程生命周期及旧 CPU 配置兼容。Web 101 项测试、TypeScript 和生产构建通过。
- Windows 原生 21 项专项测试通过，包括真实六进程启动／重启／停止与 OS CPU 绑定；另一次并发正文写入专项通过。首次并发正文专项出现既有存储路径 ValueError，后续专项及 Linux/MySQL 并发验证通过，未将 Windows 全套报告为全通过。
- 独立 MySQL 8.4：六个实际进程、OS 读取的独立 CPU 掩码、文章关键词分类、下载缺失作品跳过、单进程崩溃恢复、API 存活及 20 表导出恢复逐行一致。模型 ONNX / Intel GPU 的既有测试继续通过；本次新增的跨进程 AI 联调使用文章分类，不代表新的 GPU 真机验证。
